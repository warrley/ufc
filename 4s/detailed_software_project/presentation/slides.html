Pessoa 1

O Anti-pattern "Dual Write" 01:45 - 04:15

Fazer duas escritas independentes em sistemas heterogêneos sem transação global.

Falha A: Commit antes do Broker

1. `INSERT` pedido → `COMMIT` ✅
2. 💥 Crash da aplicação / Timeout de rede
3. `broker.publish()` ❌

Resultado: Pedido salvo, mas estoque e pagamento nunca avisados! Pedido no limbo.

Falha B: Broker antes do Commit

1. `broker.publish()` ✅
2. 💥 Erro de constraint / lock timeout no banco
3. `ROLLBACK` no banco ❌

Resultado: Estoque reservou peças para um pedido inexistente! Pedido Fantasma.

Pessoa 1 detalha os dois cenários de desastre do Dual-Write. Enfatiza a falta de atomicidade nativa entre chamadas de rede e o banco local.
Pessoa 1

Por que Try/Catch e 2PC não resolvem? 04:15 - 06:30

E se usarmos Retries (Try/Catch)?

  • Memória é volátil: Se o container reiniciar ou der OOM, retries em memória são perdidos para sempre.
  • Efeito Dominó: Threads bloqueadas esperando o broker responder esgotam o pool de conexões da API.

E quanto ao Two-Phase Commit (2PC / XA)?

  • Altíssima latência: Múltiplos round-trips de rede e bloqueios (locks) prolongados.
  • Ponto único de falha: Coordenador central.
  • Incompatibilidade: Kafka, RabbitMQ e bancos NoSQL não suportam XA.

A Ideia Central do Transactional Outbox 06:30 - 08:30

Se não podemos incluir o broker na transação do banco,
trazemos a mensagem para dentro do banco de dados!

BEGIN TRANSACTION → INSERT Pedido + INSERT Outbox → COMMIT ATÔMICO

Tabela Outbox = Caixa de Correio

Uma tabela no mesmo schema do microsserviço que guarda os eventos pendentes de publicação.

Garantia ACID Local

Ou ambos são persistidos com integridade referencial e durabilidade, ou nada é salvo.

Pessoa 2 assume. Explica o cerne do padrão criado por Chris Richardson. Mostra que o problema de rede vira escrita atômica local.

Estrutura de Dados e Sequência 08:30 - 11:00

CREATE TABLE outbox_messages (
  id UUID PRIMARY KEY,
  aggregate_type VARCHAR(100), -- 'Pedido'
  aggregate_id VARCHAR(100),   -- '123' (partition key)
  type VARCHAR(100),           -- 'PedidoCriado'
  payload JSONB NOT NULL,      -- dados do evento
  criado_em TIMESTAMP NOT NULL DEFAULT NOW(),
  processado_em TIMESTAMP NULL
);

-- Índice parcial ultra eficiente:
CREATE INDEX idx_outbox_pendentes 
ON outbox_messages (criado_em)
WHERE processado_em IS NULL;

Fluxo Atômico

  1. `BEGIN` transação local
  2. `INSERT INTO pedidos (...)`
  3. `INSERT INTO outbox_messages (...)`
  4. `COMMIT`
  5. API responde 201 Created
  6. O Outbox Relay assume em segundo plano!

O Mito do "Exactly-Once" 13:30 - 15:30

O Cenário Crítico de Falha no Relay

1. Relay lê mensagem [PedidoCriado #100] no banco.

2. Relay publica com sucesso no Apache Kafka! ✅

3. 💥 Crash da máquina / queda de rede antes do UPDATE no banco!

4. Mensagem continua como processado_em = NULL no banco.

5. Próximo worker reinicia e reenvia a mesma mensagem para o broker! ⚠️

Garantia Real: AT-LEAST-ONCE (Pelo Menos Uma Vez)

O Outbox garante que nenhuma mensagem será perdida, mas duplicações são inevitáveis!

Pessoa 3 assume. Desmistifica o Exactly-Once. Demonstra matematicamente a falha entre publicar e marcar como processado.
Pessoa 3

Consumidor Idempotente (Inbox Pattern) 15:30 - 17:15

A outra metade obrigatória da arquitetura: o receptor deve suportar duplicatas.

Idempotência por Chave Única

-- Tabela no Serviço de Estoque:
CREATE TABLE mensagens_processadas (
  mensagem_id UUID PRIMARY KEY,
  processado_em TIMESTAMP DEFAULT NOW()
);

-- Inserção defensiva:
INSERT INTO mensagens_processadas (mensagem_id)
VALUES ($1)
ON CONFLICT (mensagem_id) DO NOTHING;

Princípio de Funcionamento

  • Se o `INSERT` gravou 1 linha → Mensagem inédita → Processa estoque.
  • Se o `INSERT` gravou 0 linhas → Duplicata detectada! → Descarta com segurança.
  • A regra de negócio e a chave da mensagem comitam na mesma transação local do consumidor.
Pessoa 3 explica o Inbox Pattern / Idempotent Consumer. Mostra que a combinação de Outbox + Inbox atinge o resultado equivalente a exactly-once para o negócio.
Pessoa 3

Outbox NÃO é Saga! 17:15 - 18:45

Esclarecendo uma das maiores confusões em provas e entrevistas de PDS:

Transactional Outbox Pattern

  • Escopo: Local a um único microsserviço.
  • Objetivo: Publicação confiável de eventos sem Dual-Write.
  • Não conhece compensações nem regras de fluxo de negócio.

Saga Pattern

  • Escopo: Global entre múltiplos microsserviços.
  • Objetivo: Orquestrar transações de longa duração e rollbacks lógicos (ações compensatórias).
  • Relação: Cada participante da Saga usa o Outbox para publicar seus eventos com segurança!
Pessoa 3 desfaz a confusão conceitual. Usa a metáfora do correio (Outbox) vs contrato de negócio (Saga).
Pessoa 3

Trade-offs e Conclusão 18:45 - 20:00

Trade-offs Operacionais

  • Inchaço do Banco: Necessidade de rotinas de expurgo (Purge / Retention) para mensagens antigas.
  • Ordenação: Uso de aggregate_id como Partition Key no Kafka para preservar ordem.
  • Custo de I/O: Toda mensagem passa pelo disco antes do broker.

Por que vale a pena?

  • Elimina 100% dos desastres de consistência do Dual-Write.
  • Zero necessidade de transações distribuídas bloqueantes (2PC).
  • Auditoria nativa: o banco passa a ter histórico de todos os eventos gerados.
